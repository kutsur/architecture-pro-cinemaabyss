# To-Be Архитектура системы CinemaAbyss

## Обзор

Целевая архитектура системы CinemaAbyss представляет собой микросервисную архитектуру с постепенной миграцией от монолита. Система разделена на отдельные домены с использованием паттерна Strangler Fig для бесшовного перехода.

## Основные компоненты

### 1. API Gateway (Proxy Service)

**Технологии:** Go  
**Порт:** 8000  
**Назначение:**

- Единая точка входа для всех клиентских запросов
- Реализация паттерна Strangler Fig для постепенной миграции трафика
- Маршрутизация запросов между монолитом и микросервисами
- Поддержка feature flags для управления процентом миграции

**Основные функции:**

- Проксирование запросов к `/api/users`, `/api/payments`, `/api/subscriptions` → Monolith
- Проксирование запросов к `/api/movies` → Movies Service (с возможностью частичной маршрутизации)
- Проксирование запросов к `/api/events` → Events Service

### 2. Monolith Service

**Технологии:** Go, PostgreSQL  
**Порт:** 8080  
**Назначение:**

- Управление пользователями (регистрация, аутентификация)
- Управление платежами
- Управление подписками

**Домены:**

- **Users Domain** - управление пользователями
- **Payments Domain** - обработка платежей
- **Subscriptions Domain** - управление подписками

### 3. Movies Service (Микросервис)

**Технологии:** Go, PostgreSQL  
**Порт:** 8081  
**Назначение:**

- Управление метаданными фильмов
- Управление рейтингами
- Управление жанрами

**Домен:**

- **Movies Domain** - полная функциональность работы с фильмами

**Статус:** Выделен из монолита

### 4. Events Service (Микросервис)

**Технологии:** Go, Apache Kafka  
**Порт:** 8082  
**Назначение:**

- Обработка событий системы через Kafka
- Публикация и потребление событий

**Типы событий:**

- **Movie Events** - события фильмов (просмотр, оценка, добавление)
- **User Events** - события пользователей (регистрация, вход)
- **Payment Events** - события платежей (успешные, неудачные)

**Статус:** Новый микросервис (MVP)

### 5. PostgreSQL Database

**Технология:** PostgreSQL  
**Порт:** 5432  
**Назначение:**

- Хранение данных пользователей
- Хранение данных фильмов
- Хранение данных платежей и подписок

### 6. Apache Kafka

**Технология:** Apache Kafka + Zookeeper  
**Порт:** 9092  
**Назначение:**

- Брокер сообщений для асинхронной коммуникации
- Обеспечение событийно-ориентированной архитектуры

**Топики:**

- `movie-events` - события фильмов
- `user-events` - события пользователей
- `payment-events` - события платежей

## Паттерны и принципы

### Strangler Fig Pattern

Постепенная миграция функциональности из монолита в микросервисы:

1. API Gateway перехватывает все запросы
2. На основе конфигурации (feature flags) направляет трафик:
   - В монолит (старая функциональность)
   - В микросервис (новая функциональность)
3. Постепенное увеличение процента трафика в микросервис
4. Полное переключение на микросервис
5. Удаление функциональности из монолита

### Event-Driven Architecture

Использование Kafka для асинхронной коммуникации:

- Слабая связанность между сервисами
- Возможность масштабирования обработки событий
- Надежная доставка сообщений

### Domain-Driven Design

Разделение системы на домены:

- **Users Domain** - управление пользователями
- **Movies Domain** - управление фильмами
- **Payments Domain** - обработка платежей
- **Subscriptions Domain** - управление подписками
- **Events Domain** - обработка событий

## Интеграционное взаимодействие

### Синхронное взаимодействие

- **Клиент → API Gateway** - REST API (HTTPS)
- **API Gateway → Сервисы** - REST API (HTTP)
- **Сервисы → PostgreSQL** - SQL запросы

### Асинхронное взаимодействие

- **Сервисы → Kafka** - публикация событий
- **Events Service ← Kafka** - потребление событий

## Преимущества архитектуры

1. **Постепенная миграция** - без простоя и рисков
2. **Масштабируемость** - независимое масштабирование сервисов
3. **Надежность** - изоляция отказов
4. **Гибкость** - возможность использования разных технологий
5. **Событийная архитектура** - слабая связанность сервисов
